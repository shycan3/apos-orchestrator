# APOS Protocol

This document describes the current APOS protocol baseline for the v0.3 release line plus the runtime and bridge capabilities already committed after v0.3.

`Bridge Protocol` here means the browser-to-local integration layer, not the product version name.

APOS has two layers:

```text
Layer 1: Project Memory Layer
Layer 2: AI Bridge Layer
```

Layer 1 preserves project memory and decision history. Layer 2 converts design-oriented AI output into executable patch instructions without giving the web model direct file access.

Default server:

```text
ws://127.0.0.1:8765
```

All messages are UTF-8 JSON text frames.

## Core Terms

- `task envelope`: JSON work request generated by the web LLM
- `result envelope`: JSON execution result returned by APOS Core
- `approval item`: one queue entry that can be approved, rejected, or inspected
- `plan_only`: a task type that records a plan without executing patches or commands
- `report`: read-only failure or drift analysis produced from Recorder and Context Pack data

## Role Split

Design-oriented AI may generate ideas, critiques, risk analysis, and structured requirements.

Execution-oriented AI may generate code, edit files, run tests, and refactor.

Bridge rules:

- do not modify protected documents directly
- write proposals to `workspace/scratchpad.md` when a protected target is requested
- keep the patch envelope and the source block adjacent
- treat `sha256` as a content integrity check, not a trust signal

## ping

Request:

```json
{
  "type": "ping"
}
```

Response:

```json
{
  "type": "pong",
  "message": "APOS local server alive",
  "pending_patches": 0
}
```

## propose_patch

Request:

```json
{
  "type": "propose_patch",
  "patch_id": "patch-id",
  "project_root": "C:/Users/DO/Desktop/test-project",
  "target": "workspace/active_code.py",
  "language": "python",
  "content": "def main():\n    pass\n",
  "sha256": "..."
}
```

Required fields:

- `type`: must be `propose_patch`
- `patch_id`: unique patch identifier
- `project_root`: existing local project directory
- `target`: project-relative target path
- `language`: source language
- `content`: full final file content
- `sha256`: SHA-256 of `content`

Successful response:

```json
{
  "type": "validation_passed",
  "patch_id": "patch-id",
  "target": "workspace/active_code.py",
  "zone": "direct_candidate",
  "message": "Validation passed. Waiting for human sign-off."
}
```

Validation failure:

```json
{
  "type": "validation_failed",
  "patch_id": "patch-id",
  "error_kind": "python_syntax_error",
  "stderr": "...",
  "retry_allowed": true
}
```

Protected write redirect:

```json
{
  "type": "protected_write_redirected",
  "patch_id": "patch-id",
  "target": "specifications/core_direction.md",
  "zone": "protected",
  "message": "Protected write blocked. Proposal was appended to workspace/scratchpad.md.",
  "scratchpad": "C:/Users/DO/Desktop/test-project/workspace/scratchpad.md"
}
```

## commit_patch

Request:

```json
{
  "type": "commit_patch",
  "patch_id": "patch-id"
}
```

Successful response:

```json
{
  "type": "commit_succeeded",
  "patch_id": "patch-id",
  "target": "workspace/active_code.py"
}
```

Failure when the patch is absent, expired, already committed, or never validated:

```json
{
  "type": "error",
  "patch_id": "patch-id",
  "error_kind": "patch_not_found",
  "message": "No validated pending patch found for patch_id",
  "retry_allowed": false
}
```

## Error Rules

The server returns explicit errors for:

- invalid JSON
- non-object payloads
- unknown message type
- missing `patch_id`
- missing `project_root`
- missing `target`
- missing `sha256`
- SHA-256 mismatch
- path traversal
- absolute target paths
- null bytes
- project root escape
- unsupported language
- Python syntax failure
- duplicate patch IDs

Silent failure is not allowed.

## Human and Machine Separation

`specifications/architecture.md` uses a human notes section and a machine facts block separated by APOS tokens.

Machine parsers must only read the region between:

```text
<!-- APOS_FACTS_START -->
<!-- APOS_FACTS_END -->
```

Human notes outside that block are not machine-authored and should not be rewritten by refresh flows.

## Context Pack

Context Pack is the read-only safe summary that APOS can hand to a web LLM.

Required behavior:

- include project_name, project_root visibility, generated_at, allowed_roots, protected_roots
- summarize recent worklog entries, recent history, approval queue state, and relevant files
- mask secret-like values and omit protected file bodies
- do not carry execution privileges or raw protected documents

Markdown Context Pack output should be paste-friendly for ChatGPT or Gemini, but it is still a summary, not a source dump.

## Prompt Builder Protocol

Prompt Builder composes the current Context Pack, the user goal, and APOS safety rules into a paste-ready markdown prompt.

Modes:

- `patch`: request one APOS patch proposal only
- `plan`: request a `plan_only` envelope with a non-empty `meta.plan_steps` list
- `review`: request analysis only, with no file-edit JSON

Patch output must use exactly one `apos-patch` code block and one immediately following source block. Plan output should keep each step independently reviewable, approvable, and runnable, and review output should include a next prompt suggestion rather than a patch payload.

Output contract:

- Always keep a user-facing summary separate from APOS payloads
- In patch mode, output one `apos-patch` JSON block followed immediately by one source block
- In plan mode, output one JSON envelope with `task_type: plan_only`
- In review mode, do not output local file modification JSON

- Do not invent hidden commands or undeclared side effects
- If local state is unclear, reason only from the Context Pack

Safety fallback:

- If the request is unclear or risky, prefer review or plan mode instead of patch mode
- Do not propose direct writes to protected roots
- Command execution still has to pass APOS policy

## Failure / Drift Report Protocol

Failure / Drift Report is a read-only analysis layer built on Recorder, Context Pack, and the approval queue.

Rules:

- `report failures` summarizes recent failure records and approval rejections, but it does not mutate files.
- `report drift` compares current file timestamps and pending approval state against the Context Pack timestamp.
- `report next-prompt` returns the recommended follow-up prompt only; it does not enqueue work or execute commands.
- The dashboard may display failed approval items and drift warnings, but it still routes every action through the existing approval and plan managers.

## Recovery Prompt Protocol

Recovery prompts are paste-ready Markdown documents for a human to review and paste back into a web LLM.

Rules:

- `recover prompt` may derive its input from the latest failure, a specific failure id, a drift report, or a plan-step failure.
- It must include Recovery Goal, Failure Summary, Likely Cause, Affected Files, Relevant Context, Constraints, Required LLM Output, Recommended Mode, and Safety Reminder.
- The recommended mode may be overridden with `--mode patch|plan|review`, but the prompt must still state the recommendation clearly.
- `--mode auto` is allowed as a recommendation helper only; it may choose patch / plan / review based on failure cause, but it still must not send, approve, or execute anything.
- Recovery prompts must not auto-approve, auto-execute, or auto-send to the web model.
- If command failure is the main issue, plan mode is preferred. If the failure is a single-file patch issue, patch mode is allowed. If the cause is unclear, review mode is preferred.

## Plan Step Protocol

Plan-only tasks are stored as structured plans, and each step has its own lifecycle state.

Status model:

- `pending`: step exists but has not been approved
- `approved`: step was approved and may run
- `rejected`: step was explicitly denied
- `running`: step is currently executing
- `executed`: step finished successfully
- `failed`: step ran but failed
- `skipped`: step was not runnable under the current state

Transitions:

- `approve-step` moves a recorded step from `pending` to `approved`
- `reject-step` moves a recorded step from `pending` to `rejected`
- `run-step` may move `approved` to `running`, then to `executed` or `failed`
- `run-step` on `pending` or `rejected` returns a skipped result instead of executing
- `run-step` on `executed` or `failed` returns skipped unless the caller passes `--force`

Protocol note:

- The canonical user-facing interface is `cli/apos.py plans ...`
- `cli/plan_step.py` and `cli/plan_approve.py` remain compatibility wrappers for file-based and recorded-step workflows
